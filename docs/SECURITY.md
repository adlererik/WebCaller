# Security and privacy model

## Scope

This is an unaudited preview. Do not substitute it for independently audited software where compromise, surveillance or forensic recovery could cause serious harm. Current v2 traffic uses the Olm Double Ratchet for one-to-one transport. It is not Signal wire-compatible; the application and its integration have not had an independent audit.

## Encryption

Existing non-exportable P-256 signing/identity keys, device IDs, authentication tokens and invitation fingerprints are preserved. New v2 messages use Vodozemac 0.11.1 through a locally built Apache-2.0 adaptation of the Towns browser binding; its source, locked dependencies and build instructions are retained in [third_party/vodozemac-bindings](../third_party/vodozemac-bindings/README.md). Olm combines one-time prekey session establishment with a Double Ratchet. We explicitly require SessionConfig V2 on inbound and outbound creation and its full-length authentication tag, and reject v1/truncated-tag Olm frames. Newer library defaults must never silently select V1. Its transport uses Curve25519, AES-256-CBC, HMAC-SHA256 and HKDF-SHA256; existing ECDSA-SHA256 signatures additionally bind sender, recipient, expiry and the complete ratchet envelope. Attachment chunks use fresh per-file AES-256-GCM keys and 128-bit tags. Local records use a separate non-exportable AES-256-GCM wrapping key. Live media uses browser-negotiated DTLS-SRTP rather than these message/file ciphers. ECDSA P-256/SHA256 provides envelope/prekey signatures, and SHA256 provides identity fingerprints. The call SAS adds fresh ephemeral X25519, SHA256 commit/reveal and HKDF/HMAC-SHA256 confirmation, with a 44-bit comparison. The app does not use ChaCha20-Poly1305 for messages/files. X25519/P-256 provide roughly 128-bit classical security; AES key length is not the whole protocol security level. See the [full inventory and review](SECURITY_REVIEW.md#protocol-inventory), including its dated upgrade addendum.

The existing device signing key signs each Olm identity and one-time public key. The server checks these signatures, only lets contacts claim keys, claims each key transactionally once, and remembers claimed IDs so publication retries cannot resurrect a consumed key. Clients check signatures against locally pinned identities and also remember the accepted Olm identity. New-session identities cannot silently replace either trust record. An invitation authenticates the inviter against its link fingerprint when that link arrives through a trusted route. The inviter first learns the joiner’s keys through enrollment; compare safety numbers or the live-call SAS rather than treating a name/link as proof of a person. New contact IDs, new profiles and cleared site storage are fresh trust situations. No key transparency system is claimed. Public ECDSA envelope signatures give transferable authentication of ciphertext/headers, reducing deniability compared with symmetric one-to-one message authentication.

Consumed transport keys are discarded by the ratchet. Possession of the previous static P-256 key alone no longer derives new v2 message contents. Forward secrecy applies to discarded transport keys, and post-compromise recovery depends on fresh uncompromised DH ratchet exchanges in the affected stream after the attacker loses access; one-way symmetric-chain advancement does not heal a compromised chain, and replies on an independent events/typing stream do not refresh chat secrets; ongoing control of a device or its website code defeats it. The protocol is classical, not post-quantum. Deliberately retained readable history is a separate endpoint exposure, not erased by ratcheting.

**Browser/server trust remains:** a compromised origin can serve malicious JavaScript and use non-exportable keys, decrypt local history and capture future plaintext. /calls shares its origin with the rest of the site; a path does not isolate IndexedDB. A dedicated subdomain improves containment but does not remove trust in delivered code. DTLS-SRTP independently protects call media; the ratchet protects signaling, not individual audio/video frames. Metadata, contact relationships, sizes and timing remain visible to the server and some network/provider infrastructure.

## Upgrade and local retention

Both phones must reopen/refresh the page once after upgrading. Existing identities and invitations survive. The first publication activates v2 and takes a retryable snapshot of pre-existing v1 envelopes, including unfinished uploads and message updates. Only those exact old envelope hashes are authorized for legacy decryption. Old queued uploads can complete if their already-reserved envelope matches. Newly created v1 traffic is rejected with an update instruction; new clients never silently fall back. Historical v1 messages retain their original security limitations and do not gain forward secrecy retrospectively.

Encrypted IndexedDB records hold the Olm account/session pickles and separately sealed history. A non-exportable, independent AES-GCM wrapping key protects those records; no original static-key sender copy is sent to the server for v2. Sender history, received messages and file manifests can reopen after transport keys are discarded. Clearing this database loses that local v2 history and may require forgetting/re-enrolling the device; the server cannot recover erased transport keys. Keep this storage intact when upgrading. A ciphertext-only server backup does not recreate it.

Deletion/expiry clear authorized history and related updates, retain bounded replay tombstones until expiry, and remove cached media. A separate minimal verification fingerprint survives contact/history deletion; server roster removal cannot authorize new keys, even in another tab. Forget this device also removes the local trust records and account. This verification record is an intentional privacy/security tradeoff; contact deletion is not a promise to erase all evidence of that relationship.

The wrapping key is accessible to the same browser origin. Thus readable retained history is not protected against a compromised browser profile/origin, and JS/OS/SSD memory erasure is not guaranteed. Short-lived call/typing/transfer envelopes have sealed local copies until their own expiry so notification taps and reloads can recover already-decrypted offers. Closed browsers cannot run physical cleanup; reads reject expiry and startup/periodic purge removes expired records. Current chat and message-update ratchet records are kept, sealed under the existing device storage key, until that contact is removed or the device is forgotten. This allows Off messages to arrive after a long offline interval; unexpired pre-update session records are resealed with this storage lifetime without replacing their keys. Already expired/deleted session records are never revived. Other session lanes keep their previous seven-day inactivity cleanup, and per-file sessions are not retained. Transport keys still advance and are discarded normally, but bounded skipped-message keys within retained current chat/update sessions can remain longer. This is a storage-retention tradeoff, not a new cipher or a stronger forward-secrecy claim. Vodozemac bounds skipped keys (40 per receive chain, with a maximum forward gap of 2000); skipped keys are not guaranteed to be erased exactly at an unseen message's expiry.

## Reliability and resource use

Fenced, heartbeated IndexedDB leases serialize atomic session/history commits across tabs. A failed write returns no usable outbound envelope; invalid incoming authentication/context commits no new state. Expired leases cannot overwrite replacement state. Network key claims/publication do not hold the device-wide crypto lease, so file key requests cannot block an established call's signaling. Receiving devices replenish prekeys automatically while running; exhausted or not-yet-upgraded offline devices need to reopen the page rather than downgrade encryption.

Text, message updates, typing, transfer progress and individual calls use separate streams. Each file uses its own one-time session, then discards its transport session state: a slow upload cannot lose its key behind later chat traffic. Simultaneous first sends converge on one bidirectional conversation session. Hydration sorts public ratchet-chain counters before decrypting; live messages advance/seal crypto state while hidden without rebuilding plaintext chat UI. The protocol still has bounded out-of-order handling, not unlimited buffering or guaranteed recovery of arbitrary dropped ciphertext.

The browser loads approximately 523 KB of pinned WASM once per page instance (HTTP gzip reduces transfer size); no external runtime CDN is used. Per-message headers and cryptographic work are small relative to media. No physical-phone battery/CPU benchmark is claimed. Existing WebRTC codec adaptation, audio-first file pacing, TURN, notifications and call UI remain separate.

Library provenance, pinned hashes and upstream dependency licenses are in public/vendor/vodozemac. The core has received external review, but that does not certify this binding, this integration, or all later versions. See [Vodozemac](https://github.com/matrix-org/vodozemac) and the [Olm protocol](https://gitlab.matrix.org/matrix-org/olm/-/blob/master/docs/olm.md).

## Expiry and traces

File keys and names are wrapped inside signed encrypted message envelopes; 64 KB file chunks use AES-GCM with indexed nonces and authenticated file identity/order/size/expiry. New attachment manifests use full-tag Olm V2 ratcheting in application v2/v3 envelopes; old v1 manifests retain their long-term-key limitations. The integration remains unaudited. The server can see sizes and timing. Completed attachments are immutable and contact-only; pending uploads share bounded quotas.

Legacy timed messages expire from send time on both devices. New timed v3 messages expire from send time for the sender and first viewing for the recipient, as detailed below; unread recipient copies therefore remain available. Off has no automatic expiry. Server purge runs every second and on startup/read; client purge removes plaintext references/DOM. Backgrounding clears displayed plaintext and revokes decrypted image/file blob URLs. Expiry, participant deletion and device deletion cascade to encrypted chunks. Explicit deletion retains only message ID, participant IDs and immutable wire expiry to stop replay and inform reconnecting devices. It does not retain the envelope/key/name/content. Automatic previews download encrypted media in the open visible chat and retain decrypted blobs only in memory. Complete encrypted media chunks also persist in a separate IndexedDB cache until deletion/expiry cleanup; that cache has identity/message/file IDs, byte size, count, a per-device cleanup deadline and an optional immutable wire-expiry binding, but no plaintext, filenames, MIME types or file keys. Expiring local deletion tombstones block late-write resurrection. Remote deletion reaches an offline phone when it reconnects; server deletion markers are processed before media rehydration. Cache reads/writes reject expired content; physical cache purging cannot run while the browser is closed and occurs on next startup/foreground and periodically while running. Browser/OS storage can retain forensic remnants or evict cached data. Forget this device clears local encrypted media, but cannot erase other devices while they are offline. Camera and voice drafts are discarded on backgrounding; native camera/download copies remain under OS control. Typing statuses are signed/encrypted and not stored/replayed by the server; no draft text is transmitted. The client seals short-lived crypto reload copies until envelope expiry (currently 10 seconds for typing and at most 20 seconds for transfer progress), without creating visible chat-history entries. Chat is hidden from print layouts. These actions cannot prevent OS screenshots, screen recording or photographing a display. No persistent plaintext outbox/cache is created. SQLite uses `secure_delete=ON` and DELETE journaling for operational deletion, not guaranteed forensic erasure on SSDs/snapshots/backups.

Device keys/tokens, names, contacts and settings persist. Screenshots, browser history, camera/share history, OS notification history, DNS records, push/provider metadata, swap, recipients' external copies and backups may remain. HTTPS/Tunnel/proxy/operator logs can reveal metadata. A website cannot guarantee zero traces.

## Authentication and signaling

First-owner setup requires its private setup secret while no users exist. Additional devices can redeem an invitation or deliberately dial an enabled public calling code; code enrollment creates a new identity and a limited pending contact request, never access to an existing identity. The private QR/link contains that same bearer secret; keep it private. If all users are deleted the code can become eligible again. Invitations expire after 24 hours, are single use and pin the inviter fingerprint. API bearer tokens are hashed in server storage; device possession grants access. Origin enforcement, contact authorization, body limits, rate limits, no-store, CSP, framing/referrer/permissions headers and short-lived single-use WebSocket tickets are used. Tokens are not placed in WebSocket URL query strings.

Push subscription endpoints are restricted to known HTTPS provider hosts to reduce SSRF risk. Notifications are generic. Coturn has temporary REST HMAC credentials, quotas and denied private/multicast peer ranges. Never expose unauthenticated TURN or enable browser certificate-warning bypasses.

## Publishing safely

The repository/release contains source, tests, examples and documentation. It excludes `.env`, databases, identities, runtime/private QR output, certificates/keys, deployment backups, logs, dependency folders and production diagnostics. Examples use reserved domains and explicit user-supplied server addresses. `npm run audit:source` checks Git-tracked files for private file types and common credential literals. Deployment-specific addresses and names require a separate manual review. This is a focused guard, not a professional security audit. Review new data/assets before committing and rotate a secret if it was ever published; deleting a later commit does not erase Git history.

## Call-alert data

Invitations now optionally hold a recipient name until redemption/expiry. During iPhone Home Screen setup, the invitation fragment stays in the address for launch handoff. It is cleared after acceptance and only its hash is retained to recognize a previously consumed launch link. Browser/Home Screen metadata and a user-copied clipboard may still retain that original URL. Fragments are never sent in HTTP URLs or referrers. A Home Screen web app has its own browser identity; existing browser keys/contacts are not silently transferred or reset. Use a fresh invitation for a new Home Screen identity.

Push contains generic text, type, opaque call/test ID and deadlines, without names, SDP, keys or message bodies. Push-provider endpoints/subscription keys remain server-held. The worker reads the existing browser vault token to check call state on the same origin. Test records live in server memory for ten minutes and bind to owner and subscription; confirmation timestamps persist until that subscription changes or is removed. The browser keeps an unfinished test ID/deadline to resume after notification tap. Phone sound confirmation is a user report, not a delivery or audibility guarantee.

## Location privacy

Location is optional, one-shot and previewed before Send. Coordinates/label/accuracy/capture time and the thumbnail are encrypted using the existing attachment/message format. Sender map-tile requests disclose map area/IP to the configured provider. The map image is transmitted to the recipient as encrypted media; receiving it does not automatically load third-party map tiles. Tapping Maps sends coordinates to that external service. Normal tile caches, browser history and provider metadata may remain after message expiry/deletion. The app’s no-store ciphertext policy does not erase external tile caches. Never claim zero location traces. Map provider configuration is public; do not embed private API keys. Only that provider’s image origin is added to CSP, and geolocation/speaker-selection are allowed for self only.


## Message actions and receipts

Edits, emoji reactions, pins and receipt timestamps are signed/encrypted with the same device keys as chat. The server sees participant IDs, target message IDs, event kinds, update time and expiry, but not the edited text or emoji. Legacy read/delivery timestamps remain inside the encrypted payload; new v3 first-view receipts expose the authenticated start timestamp needed for server retention. It retains only the latest state per participant and kind. Updates cannot extend original expiry and are deleted with the parent message/device.

An edit updates the visible message, but the original encrypted message envelope remains until deletion/expiry; this is not forensic erasure of the prior text. A recipient, forwarded copy, downloaded file, clipboard or screenshot may retain content. Replies avoid keeping a quoted plaintext copy after original deletion/expiry. A viewed acknowledgement is based on visible app UI, not an assurance a human read it. The timestamp comes from the recipient device clock. Pins never defeat disappearing-message expiry.

Call sharing keeps the same encryption and expiry rules. The server temporarily stores small ciphertext parts, never their file key or plaintext, and only assembles them into authenticated ciphertext chunks. Incomplete parts disappear with the reserved attachment on cancellation, device removal or expiry. Capability summaries contain codec variants and efficiency booleans inside encrypted call signaling; hardware implementation names are not sent. Calls remain subject to the same DTLS-SRTP and origin-trust limitations.


## Removing a contact

Contact removal is participant-scoped and guarded by bearer authentication and origin validation. The server atomically removes both contact rows, this pair’s ciphertext messages, attachments (including incomplete uploads), encrypted message events and all chunk/part records. Other conversations remain. It ends this pair’s waiting/active call and stops reminder timers. Idempotent retries return no information about conversations the requester does not participate in.

Only deleted message IDs, participants and original expiry remain as replay barriers; there is no message content in those markers. Legacy markers expire with the originals. Off and new per-view messages use durable ID-only barriers because their immutable wire envelopes have no finite expiry. They also let a closed browser evict cached ciphertext after reconnecting. Local full contact entries/settings, displayed plaintext and drafts are cleared on removal. Minimal P-256 and Olm verification records remain, preventing contact deletion from resetting trust for the same contact identity; forgetting the device/site storage clears them. Saved files, forwarded copies, screenshots, offline devices before reconnecting, browser/OS traces and external backups cannot be guaranteed erased. Deployment source backups do not contain the application database; operators should set their own data-backup retention policy.

## Notification actions

High urgency requests fast delivery, not privileged audio. No background microphone or custom continuous ringtone is attempted. Notification sound/banners remain subject to user and OS controls. A one-time IndexedDB answer decision contains only owner ID, call ID and a deadline capped at 30 seconds; no secret or content is added. It is consumed/deleted atomically and rejected after expiry or for another identity. The page also checks a signed encrypted incoming offer and authenticated waiting status while visible. URLs cannot auto-answer calls. Expired metadata may remain on disk while the browser is suspended, and is cleared on consumption, call end or forgetting the device. Background decline is authenticated, origin checked, recipient only, and refuses already answered calls. Notification history can remain under OS control.

## Browser history and message routing

A website cannot erase browser/global or synced history, OS notification records or evidence of its service worker, notification permission, saved identity and cached ciphertext. Normal history deletion is a browser/user operation, not a website API. No IDs or names are added to conversation URLs; notification message routing uses only opaque IDs in a short-lived identity-bound local record, removed on consumption/forgetting the device. Neutral notification wording protects visible content, not the existence of the website. Suspended browsers may retain expired metadata until they run again. Persistent phone identity and cached media remain as required for returning calls and local reopening. See [Browser privacy](BROWSER_PRIVACY.md).

Transfer progress remains encrypted and only in client memory. It is never persisted as chat history or server events; its sender must own a live reservation. Late progress cannot restore a committed/deleted attachment, and its short lease expires if connectivity is lost. Countdown updates do not change expiry or mark a message read by themselves.


## Optional call SAS (v0.14)

The caller and callee can compare four English words aloud. No confirmation button, stored human-verification flag, green verification badge or call gate is present. Ignoring the words leaves the existing cryptographic protections unchanged. Matching words are an additional human check under trusted client code, not a guarantee of identity, anonymity or freedom from malicious website code.

A separate ephemeral X25519 exchange uses the already bundled Vodozemac SAS primitive. The caller commits with SHA-256 before the callee reveals a fresh public key and nonce. The caller reveal must match that commitment. HKDF-SHA256/HMAC-SHA256 binds both contributions, the protocol domain, call ID, caller/callee roles, existing pinned public identities and both DTLS fingerprint sets. Direction-specific key confirmations are checked before displaying four 11-bit word indices (44 bits). This is a WebCaller-specific protocol integration inspired by commitment-based SAS designs, not Matrix or ZRTP wire compatibility, and has not been independently audited.

No Olm root/chain keys are exported. SAS frames travel inside existing signed Olm v2 call signaling, only between the active, answered call participants. Their plaintext is excluded from the local history archive; the server forwards them without storing a SAS transcript. Fresh SAS private keys, derived secret and MAC key material are managed/freed by the crypto library. Remaining call-only public transcript, words, timers and DOM accessibility attributes are released at hang-up. JavaScript/OS memory erasure is best effort. Existing Olm accounts/session state and identity pins continue using their existing encrypted storage; this feature does not make the entire application stateless.

Handshake timeout, bounded retries, unsupported old clients and validation failure affect only the word display. ICE/address/codec changes preserve the words when media identities remain unchanged; replacement DTLS fingerprints invalidate the display and create a fresh check. See [protocol and UI details](CALL_VERIFICATION.md).

## Optional ntfy alert transport

Confirmed ntfy recipients use one preferred call-alert transport. Browser push remains the fallback for a publishing rejection/timeout and remains enabled for messages; acceptance is not proof of phone delivery or sound. A per-device preference preserves the existing topic and heard-test confirmation. An additive `preferred` column defaults existing subscriptions to ntfy while preserving identity/authentication and ratchet records. Notification links only open a waiting recipient call through its authenticated, signature-checked encrypted offer. They cannot create an answer intent or activate capture.

The ntfy integration sends generic alerts and opaque opening references only; it never transports conversation keys, signed SDP, chat or media. The native read address is a separate random 256-bit capability, while a write-only publishing token stays server-side. An alert cannot authenticate or automatically answer a call. Existing Olm, pins, SAS and DTLS-SRTP checks still apply. The additional service runs isolated from WebCaller files; compromised alert delivery can still cause spam/missed alerts. Read the full [boundary, retention and iPhone relay limitations](EXTRA_RINGING.md#security-and-privacy-boundary).

### Prebuilt Docker trust and isolation

The optional v0.16 Docker bundle runs the same phone code. Published bundles pin project and upstream images by digest; GitHub Actions tests native amd64/arm64 stacks before publishing. Image/release integrity remains dependent on the maintainer, GitHub/registry access, build dependencies and the host. SHA-256 checksums fetched beside a release are not an independent signature or an audit.

The app and ntfy have separate data/state mounts. A network-disabled one-shot helper creates ntfy's deny-all/read-capability ACLs and write-only publisher token, stored in a dedicated volume mounted read-only by the app. Runtime ntfy cannot read the app environment/database or its publisher-token volume. The app does not receive the Docker socket. Setup creates secrets at installation time; images/releases contain no live configuration.

For this bundle only, `NTFY_ALLOW_DOCKER_HTTP=true` permits exactly `http://ntfy:8094`; without it, HTTPS/loopback rules remain. This is plaintext on an isolated same-host Docker bridge, including the alert publisher credential, not TLS between containers. Compromise of that network/host can expose the alert token/metadata; it still supplies no chat/media/ratchet/SAS keys or caller authentication. No redirect is followed with the token. External clients use the separate HTTPS ntfy origin. `_FILE` credentials fail closed if unreadable and cannot be set alongside an inline token.

Updates preserve volumes/configuration, reject downgrades and require an explicit newer release. Startup checks are not cryptographic migration proofs. No automatic conversation archive is created; manually retained backups can outlive disappearing timers. Read the release's migration notes and keep a matching private backup if your recovery policy requires one. Existing endpoint, browser-origin, metadata and independent-audit limitations remain.

## Calling-code enrollment

Optional 4–12 digit addresses add first contact without invitations. They are public directory entries, not passwords or encryption material. New browsers persist fresh private device keys and a cryptographically random 256-bit bearer token before enrollment; existing phones reuse their identity and token. Enrollment is idempotent for that saved device and never recovers or overwrites an existing identity. Codes are opt-in, unique and reserved to the same identity after disabling/changing until the identity is deleted. Returning clients bind remembered codes to the original contact ID; all existing public-key/Olm identity pins still apply.

The initial directory mapping has weaker authentication than an invitation fingerprint delivered over a trusted channel. The Olm/SAS/media protocols are unchanged; code lookup does not authenticate a first correspondent by itself. Compare the four SAS words on a trusted voice call before sensitive first-contact text. This is not key transparency. Server-side rate limits, bounded request counts, five-message limits, acceptance before media uploads and identity blocking limit abuse but cannot establish a real person’s identity or stop all new-identity evasion. A server owner can disable the feature with `DIAL_CODES_ENABLED=false`. See [Calling codes](CALLING_CODES.md).

## Message lifetimes: timed or Off

Existing v2 chat, file and message-update envelopes support signed finite lifetimes of up to 28 days. Off uses the exact safe-integer expiry sentinel `8640000000000000` within the existing signed header and encrypted framing. It is accepted only for these persistent v2 lanes; signaling, typing and transfer notices cannot use Off. Legacy v1 envelopes retain the seven-day bound and short call signaling retains its 120-second bound. Only the original sender can edit. Legacy updates are bounded by their parent’s wire expiry; per-view update history is limited by each device’s deadline, with timing/replay exceptions described below. Off does not extend existing messages. Older clients must refresh before reading the new lifetime options.

Off retains encrypted history, attachment ciphertext and deletion replay barriers until deleted rather than promising automatic erasure. Legacy timed envelopes keep their existing expiry behavior; new per-view timers are described below; no expired history is restored by the ratchet-state lifetime migration. Uncommitted file reservations have a maximum 24-hour inactivity lease (renewed by valid upload chunks, bounded by any shorter signed expiry). Committing a complete file applies its parent message lifetime, including Off. Quotas continue to apply, so Off files may need manual deletion to free space. Browser transfer alarms split long finite waits into safe timeout intervals and do not arm expiry timers for Off. Settings changes do not change cryptographic identities, identity pins, the Vodozemac engine, SAS or media encryption.

## Independent sender and recipient timers (application envelopes v3)

New timed text/file envelopes authenticate `lifetime: {mode: "after-view", seconds}` in both the ECDSA-signed header and the header inside Olm ciphertext. The immutable wire expiry uses the existing safe-integer sentinel. This is **application envelope version 3**, not a different Olm protocol: full-tag Olm V2, Vodozemac, Curve25519, AES/HMAC, device identities, pins and call SAS remain unchanged. Existing v1/v2 messages and v2 signaling keep their original framing and lifetimes. Off remains v2. Both browsers must refresh before using new timed messages.

The sender’s sealed history expires at creation plus the chosen duration. The recipient’s sealed first-view record starts its own deadline once, atomically across tabs, and cannot be restarted by reopening the chat. The server filters text, updates and committed files by each participant’s deadline. A new recipient-only, signed `view-receipt` header binds the parent ID and first-view time; the encrypted read payload binds those same fields. The server verifies v3 signatures, rejects changes to the first-view time, and deletes the shared ciphertext after both deadlines. Read-start receipts may retry outside the normal five-minute submission window only for the authenticated recipient and a still-known parent. Other old packet submissions retain their existing limits.

**Retention tradeoff:** an unread recipient copy has no automatic unread deadline. Its ciphertext and the receiver’s sealed local reload copy can remain until it is viewed or explicitly deleted, even after the sender’s own copy disappears. This feature therefore changes retention, not the strength of encryption. Read timing/duration and routing are server-visible metadata. Pending read-start metadata and a sealed signed-ciphertext outbox survive suspension/reload, including expiry of the visible copy; they retry on reconnection. No message text is placed in that outbox. Network loss, a closed browser or an uncooperative recipient can delay cleanup; an offline/compromised recipient can keep copies in any case. This is not a promise of zero forensic traces.

Attachment chunk authentication stays bound to the immutable wire expiry. Local ciphertext-cache deadlines shorten at first viewing without another download or re-encryption. Local expiry removes retained message text/file keys and cached media, with ID-only replay barriers preventing the indefinite wire envelope from restoring an expired copy. The server also writes durable ID/participant replay barriers before timed v3 cleanup; explicit contact/device removal retains its established behavior. Small digest-only update reload records, containing an expired marker and target ID instead of edit text, absorb recent duplicate echoes for up to two minutes. Pending timing metadata is removed after acknowledgement and local expiry; contact/device removal clears the relevant local state. The wrapping key remains usable by the same browser origin, so endpoint/origin compromise remains a major limitation.

## 200 MiB attachment handling

The larger limit and adaptive concurrency change transport/storage policy, not the cipher. A fresh random 256-bit file key and 64-bit random nonce prefix remain inside an Olm-ratcheted, signed manifest. Each 64 KiB chunk adds its unique 32-bit index to form the 96-bit AES-GCM nonce; a 200 MiB file uses 3200 distinct indices. The 128-bit tag authenticates file identity, index, total plaintext size and immutable wire expiry. Retrying transmits the same ciphertext; it does not re-encrypt changed plaintext with an old nonce. Chunk length/order/identity/tag checks precede display. Do not replace this with an unauthenticated streaming cipher.

Parallelism is bounded to four client workers and eight server requests per account. Request bodies, token-bucket rate, 200 MiB file size and per-account/global reservations bound resource use. Defaults reserve at most 1024 MiB per sender and 4096 MiB globally; operators can lower or raise those explicit limits. Pending uploads have a renewable bounded lease and are not readable by recipients before commit. A larger quota exposes more disk/traffic to an authorized abusive account, so keep a suitable server disk budget.

Local cache schema version 2 stores ciphertext chunks incrementally under a generation-bound complete manifest. It stores no file keys, names, types or plaintext. Deletion invalidates pending generations and removes chunks; expiry and first-view retiming apply to committed cache data. Old version-1 records remain readable. A closed/suspended browser cannot execute physical cleanup; staging leases, purge-on-return and browser storage/forensic limitations still apply. Download/display Blobs remain plaintext in browser memory while in use; this does not create guaranteed secure memory erasure. Backgrounding still clears displayed media and cancels transfer work.

Adaptive speed is not a cryptographic control, an anonymity mechanism or an assurance of uninterrupted audio. More bytes/timing and prolonged unread delivery remain visible as metadata to the server/network. Olm forward-secrecy limits, browser-delivered-code trust, per-call SAS comparison and endpoint compromise risks are unchanged.
